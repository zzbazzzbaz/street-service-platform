## 2. 通用约定

### 2.1 基础地址与鉴权

- API 基础地址：`https://commu.iloveminmeng.com/api`。
- 小程序接口：`Authorization: Bearer <user_access_token>`。
- 街道后台接口：`Authorization: Bearer <admin_access_token>`。
- 用户记录接口只能返回当前 token 所属用户的数据，不接受前端传入任意用户 ID 查询他人记录。

### 2.2 响应格式

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

分页响应的 `data`：

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 20
}
```

失败响应必须提供可直接定位字段或业务规则的中文信息：

```json
{
  "code": 40000,
  "message": "商户分类不在允许范围内",
  "data": null,
  "errors": {
    "category_code": ["无效的商户分类"]
  }
}
```

## 3. 商户字段扩展

### 3.1 新增字段

| 字段 | 类型 | 请求/响应 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `category_code` | string | 是 | 使用 3.2 枚举 | 商户性质，用于选择小程序图标 |
| `business_hours` | string | 是 | 建议 1-100 字，纯文本 | 营业时间，允许星期、休息日和分时段 |
| `service_content` | string | 是 | 建议 1-500 字，纯文本 | 面向居民提供的主要商品或服务 |

`business_hours` 使用纯文本，不拆成固定的开始、结束时间。例如：

```text
周一至周五 08:00-18:00，周六 09:00-16:00，周日休息
```

`service_content` 不接收 HTML。后端应去除首尾空格、过滤危险内容并限制长度。

### 3.2 商户分类枚举

| `category_code` | 含义 |
| --- | --- |
| `food` | 餐饮商户 |
| `retail` | 零售商超 |
| `repair` | 维修服务 |
| `healthcare` | 医药健康 |
| `life_service` | 生活服务 |
| `other` | 其他商户 |

业务规则：

- 分类必须由街道后台选择并持久化，不根据商户名称、地址或服务内容推断。
- 新建商户未明确选择时可以默认 `other`。
- 非枚举值返回 HTTP `400` 和明确字段错误。
- 后端不得返回临时中文值或其他未约定代码。

## 4. 小程序商户列表接口

### 4.1 调整接口

```http
GET /api/merchants?page=1&page_size=100
```

认证：用户 token。

列表每项至少返回：

```json
{
  "id": 12,
  "name": "便民家电维修店",
  "contact_name": "王师傅",
  "phone": "13800000000",
  "address": "椿树街道社区服务站东侧 20 米",
  "latitude": 39.908823,
  "longitude": 116.397470,
  "category_code": "repair",
  "business_hours": "周一至周日 08:00-19:00",
  "service_content": "提供小家电检测、维修及上门取送服务",
  "is_active": true
}
```

业务规则：

- 新增三个字段直接放在列表项中，不要求前端逐个请求商户详情。
- `latitude`、`longitude` 使用 GCJ-02，必须同时为空或同时有值。
- 不向普通用户返回商户 OpenID、固定积分码明文或后台内部字段。
- 停用商户可以由接口直接排除；若继续返回，必须准确返回 `is_active = false`。

## 5. 街道后台商户管理接口

### 5.1 后台列表

```http
GET /api/admin/merchants?page=1&page_size=50
```

每个商户必须返回 `category_code`、`business_hours`、`service_content`，用于编辑回显。

### 5.2 新建商户

```http
POST /api/admin/merchants
```

请求示例：

```json
{
  "name": "便民家电维修店",
  "category_code": "repair",
  "contact_name": "王师傅",
  "phone": "13800000000",
  "address": "椿树街道社区服务站东侧 20 米",
  "business_hours": "周一至周日 08:00-19:00",
  "service_content": "提供小家电检测、维修及上门取送服务",
  "latitude": 39.908823,
  "longitude": 116.397470,
  "is_active": true
}
```

成功响应返回保存后的完整商户对象，包含新增字段。

### 5.3 编辑商户

```http
PATCH /api/admin/merchants/{merchant_id}
```

接口需要允许修改：

- `category_code`
- `business_hours`
- `service_content`
- 原有名称、联系人、手机号、地址、坐标及启用状态

成功响应返回保存后的完整商户对象。

### 5.4 数据迁移与校验

- 为存量商户补默认 `category_code = other`，不得自动猜测分类。
- 存量商户的营业时间和服务内容允许迁移期间暂时为空，由运营人员补录。
- 启用商户原则上必须补全地址、分类、营业时间和服务内容。
- `business_hours`、`service_content` 超出长度限制时返回 HTTP `400` 和字段错误。
- 停用商户保留历史积分支付和结算记录，不级联删除。
- 商户手机号仍用于微信登录绑定，本次字段扩展不得改变现有登录逻辑。

## 6. 随手拍与爱心善举筛选

### 6.1 调整接口

```http
GET /api/reports?report_type=report|good_deed
```

筛选规则：

- `report_type=report`：排除 `category_code=good_deed`。
- `report_type=good_deed`：只返回 `category_code=good_deed`。
- 不传 `report_type`：返回当前用户全部上报记录。
- 响应继续返回现有 `category_code`，不要求新增重复的 `report_type` 响应字段。
- 必须在数据库查询层完成筛选，不能先分页再过滤，否则 `total` 和分页结果不准确。

普通随手拍使用以下分类：

| `category_code` | 含义 |
| --- | --- |
| `safety_hazard` | 安全隐患 |
| `environmental_hygiene` | 环境卫生 |
| `public_facility` | 公共设施 |
| `other` | 其他 |
| `good_deed` | 爱心善举，不属于普通随手拍 |

## 7. 志愿任务与线下活动分类

### 7.1 分类字段

| `activity_type` | 含义 |
| --- | --- |
| `volunteer` | 志愿任务 |
| `offline` | 线下活动 |

`activity_type` 必须持久化，不能根据标题、当前入口或其他文本推断。

### 7.2 接口要求

以下用户接口必须返回 `activity_type`：

- `GET /api/activities`
- `GET /api/activities/{activity_id}`
- `GET /api/activities/my-signups`

列表接口支持查询参数：

```text
activity_type=volunteer|offline
```

以下后台接口也需要支持读写 `activity_type`：

- 活动列表。
- 活动详情。
- 活动创建。
- 活动编辑。

业务规则：

- 报名和签到记录通过关联活动获得同一 `activity_type`。
- 已产生报名记录后，建议禁止修改活动类型。
- 后端应禁止用户报名 `end_time <= 当前时间` 的活动，不能只依赖前端限制。

## 8. 统一服务记录


### 8.1 统一列表

```http
GET /api/service-records?page=1&page_size=20
```

要求：

- 只返回当前登录用户自己的记录。
- 不提供分类筛选，按 `occurred_at` 倒序返回全部类型。
- 收录没有积分入账的待审核、驳回、取消、未签到等真实服务事件。
- 人工积分调整不属于服务事件，不进入统一记录。
- 返回稳定的 `record_type`、`source_id`、状态、状态中文、积分和发生时间。

### 8.2 统一详情

```http
GET /api/service-records/{record_type}/{source_id}
```

要求：

- 校验记录属于当前登录用户，否则返回 HTTP `403` 或 `404`。
- 返回列表字段及完整正文、图片、地点、审核意见、回复和相关时间。
- `image_urls` 统一返回数组，没有图片时返回 `[]`。
- 图片地址必须是微信真机可访问的 HTTPS 地址。

## 9. 后端验收标准

### 9.1 商户接口

- 新建、编辑和列表接口均能保存并返回三个新增字段。
- 六种 `category_code` 均按约定返回，非法值被拒绝。
- 后台修改营业时间或服务内容后，小程序列表立即可以读取最新值。
- 普通用户接口不泄露 OpenID、固定积分码或后台内部字段。
- 停用商户不会作为可用兑换网点展示。

### 9.2 上报、活动与统一记录

- 随手拍与爱心善举在服务端正确筛选，分页总数准确。
- 志愿任务与线下活动列表、报名记录互不混合。
- 活动结束后，直接调用报名接口也会被后端拒绝。
- 统一记录按时间倒序返回全部真实服务事件，包括未获得积分的记录。
- 统一详情能返回完整事件内容，并正确校验用户归属。

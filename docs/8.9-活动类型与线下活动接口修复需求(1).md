# 活动类型与线下活动接口修复需求

更新时间：2026-08-10  
适用范围：用户端小程序、街道管理后台 H5 的志愿任务与线下活动接口

## 1. 当前问题

用户端进入“线下活动”页面时，部分环境会提示“活动接口未返回匹配的 activity_type”。前端请求线下活动时会传递 `activity_type=offline`，并校验返回的每一条记录都必须是 `offline`。出现以下任一情况都会导致页面无法正常展示：

- 服务端没有真正按 `activity_type` 筛选，仍返回志愿任务；
- 活动记录的 `activity_type` 为空或没有被序列化返回；
- 历史活动没有完成类型数据迁移；
- 我的报名接口没有接收类型参数，或报名记录没有从关联活动取得类型；
- 后台查询接口只能返回混合数据，导致审核页面只能依赖前端临时过滤。

线上 OpenAPI 当前已声明 `GET /api/activities` 的 `activity_type` 参数，但 `GET /api/activities/my-signups`、`GET /api/admin/activities`、后台报名和签到列表接口仍未完整提供对应筛选能力。请按下列要求补齐并确认已部署到实际 API 环境。

## 2. 数据与业务规则

### 2.1 活动类型

活动表必须持久化以下枚举值：

| 值 | 含义 |
| --- | --- |
| `volunteer` | 志愿任务 |
| `offline` | 线下活动 |

要求：

- 新建活动必须明确写入 `activity_type`；未传值时可按兼容策略默认为 `volunteer`，但不能保存为空；
- 历史数据必须完成迁移，原志愿任务写为 `volunteer`，线下活动写为 `offline`；
- 活动列表、活动详情、报名记录和签到记录均不得返回空的 `activity_type`；
- 报名和签到记录的类型必须通过关联活动获得，不接受客户端自行传入的类型作为真实数据；
- 已产生报名记录的活动不建议再允许修改 `activity_type`，至少要避免修改后造成历史报名记录分类错误。

### 2.2 活动结束后禁止报名

`POST /api/activities/{activity_id}/signup` 必须在服务端校验：当 `end_time <= 当前服务端时间` 时拒绝报名，返回 HTTP 400，并在 `message` 中明确说明“活动已结束，无法报名”。该校验不能只依赖小程序前端。

## 3. 用户端接口

### 3.1 活动列表

```http
GET /api/activities?activity_type=volunteer|offline&page=1&page_size=20
```

要求：

- 支持 `activity_type` 查询参数；
- 仅允许 `volunteer`、`offline`，其他值返回 HTTP 400；
- 在数据库筛选完成后再分页，`total` 必须是筛选结果的总数；
- 传 `activity_type=offline` 时只能返回线下活动，不能混入志愿任务；
- 没有匹配数据时返回正常空分页，不返回异常；
- 每一项都返回正确的 `activity_type`；
- 不传类型时可以返回全部已发布活动，但每项仍必须带有类型字段；
- 继续遵守已存在的发布状态、启用状态和时间范围规则。

### 3.2 活动详情

```http
GET /api/activities/{activity_id}
```

要求：

- 返回 `activity_type`；
- 返回的类型必须与活动列表及活动数据库记录一致；
- 活动不存在或不可展示时返回明确的 404/业务错误，不返回缺字段的半完整对象。

### 3.3 我的报名记录

```http
GET /api/activities/my-signups?activity_type=volunteer|offline&page=1&page_size=20
```

要求：

- 增加并实际处理 `activity_type` 查询参数；
- 先按当前登录用户和活动类型筛选，再分页；
- 每条记录返回正确的 `activity_type`；
- `activity_type=offline` 时只返回线下活动报名，`volunteer` 时只返回志愿任务报名；
- 没有记录时返回正常空分页；
- 保留报名、取消、签到、积分状态等现有字段，不能因为补类型字段而改变原有状态含义。

## 4. 后台活动管理接口

### 4.1 活动列表

```http
GET /api/admin/activities?activity_type=volunteer|offline&status=...&page=1&page_size=20
```

要求：

- 增加可选的 `activity_type` 筛选；
- 后端完成筛选和分页，返回准确 `total`；
- 每项返回 `activity_type`；
- 不同类型活动不能在同一类型筛选结果中混合出现。

### 4.2 活动创建与编辑

以下接口需要支持读写并返回 `activity_type`：

```http
POST /api/admin/activities
PATCH /api/admin/activities/{activity_id}
```

要求：

- 只接受 `volunteer`、`offline`；
- 保存成功后响应对象必须返回实际保存的类型；
- 对历史活动补齐默认类型，不能让后台返回 `null`；
- 如活动已有报名或签到记录，建议禁止修改类型并返回明确的业务错误。

### 4.3 报名与签到审核列表

当前后台接口只有分页参数，前端只能先拉取混合数据再按活动 ID 临时过滤。请为以下接口补充类型字段和服务端筛选：

```http
GET /api/admin/activities/signups?activity_type=volunteer|offline&page=1&page_size=20
GET /api/admin/activities/checkins?activity_type=volunteer|offline&page=1&page_size=20
```

要求：

- 支持 `activity_type` 可选筛选，并在服务端完成；
- 每条报名、签到记录返回从关联活动取得的 `activity_type`；
- 筛选后再分页，`total` 与结果一致；
- 线下活动审核列表不能出现志愿任务记录，反之亦然；
- 保持现有报名状态、签到状态、审核状态和积分发放字段不变。

如接口还支持按 `activity_id` 筛选，建议同时提供该参数，以减少后台审核页面不必要的数据量，但不是本次联调的必要前提。

### 4.4 报名与签到响应的业务字段

线上 OpenAPI 当前将后台报名和签到列表响应声明为通用字典，无法确认实际响应是否包含后台页面所需的用户信息。请确保实际返回至少包含以下字段：

| 记录 | 必须返回字段 |
| --- | --- |
| 报名记录 | `id`、`activity_id`、`activity_type`、`title`、`member_id`、`member_name`、`member_phone`、`signup_status`、`checkin_status`、`point_status`、`created_at` |
| 签到记录 | `id`、`activity_id`、`activity_type`、`activity_title`、`member_id`、`member_name`、`member_phone`、`status`、`review_comment`、`point_record_id`、`created_at` |

要求：

- `member_name`、`member_phone` 必须从报名/签到关联的用户记录读取，不要固定返回“用户-”或只返回用户 ID；
- `activity_title`、`activity_type` 必须从关联活动读取；
- 历史报名和签到记录即使关联的是旧活动，也不能因为缺少新字段导致整页 500；
- 建议同步补充 OpenAPI 的响应模型，避免接口文档显示为 `dict` 而无法联调。

### 4.5 用户签到响应

```http
POST /api/activities/{activity_id}/checkin
```

签到成功、待审核或被拒绝的响应都应返回 `activity_type`，并与活动本身保持一致。签到记录写入时不得由客户端传入或覆盖活动类型。

## 5. 接口验收标准

请使用至少一条志愿任务和一条线下活动进行联调，并验证以下场景：

1. 调用 `/api/activities?activity_type=offline`，返回的所有记录均为 `offline`；
2. 调用 `/api/activities?activity_type=volunteer`，不会返回线下活动；
3. 两类活动都能在详情接口中返回正确类型；
4. 用户分别报名两类活动后，`/api/activities/my-signups?activity_type=offline` 和 `volunteer` 的结果互不混合；
5. 用户没有某一类型报名记录时，接口返回空分页而不是 500 或类型错误；
6. 后台两类活动管理、报名审核、签到审核页面的数据互不混合，分页总数准确；
7. 将旧数据中类型为空的活动全部修复后，任意活动列表和报名记录都不再出现空类型；
8. 对已结束活动直接调用报名接口会被服务端拒绝；
9. 后台报名和签到记录可以显示真实活动名称、用户姓名和手机号，不出现固定测试姓名或空字段；
10. 以上接口在实际部署地址 `https://commu.iloveminmeng.com/api` 上验证，不只更新本地代码或 OpenAPI 文档。

## 6. 媒体地址生产环境复查

历史联调记录中，随手拍、帮扶记录和学习内容曾出现 `http://commu.iloveminmeng.com/media/...` 地址。请在实际生产数据中抽样检查以下接口的图片、封面和视频地址：

- `GET /api/learning/contents`
- `GET /api/reports`
- `GET /api/reports/{report_id}`
- `GET /api/elder-services/feedbacks`
- `GET /api/service-records/{record_type}/{source_id}`

如果仍返回 `http`，后端需要统一改为可被微信真机直接访问的 `https://commu.iloveminmeng.com/media/...`，并检查反向代理的 `X-Forwarded-Proto` 和应用的 HTTPS 配置。接口应直接返回最终 HTTPS 地址，不依赖 301 跳转。

## 7. 优先级

- **P0**：活动数据类型迁移、用户活动列表筛选、我的报名列表筛选及类型返回。这些问题会直接导致线下活动页打开失败或展示错误数据。
- **P1**：后台活动列表、报名审核和签到审核的服务端类型筛选及真实用户信息返回。这会影响后台两类业务的准确管理和分页性能。
- **P1**：结束活动的服务端报名拦截，避免绕过小程序前端限制产生无效报名。
- **P1**：媒体资源统一返回 HTTPS，避免微信真机出现裂图或视频无法加载。

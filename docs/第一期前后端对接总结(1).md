# 第一期前后端对接总结

## 已按现有接口接入的用户端功能

1. 用户登录基础链路
   - 已配置用户端默认接口地址为 `https://8000.frp.chatgqt.top/api`。
   - 已新增统一请求封装，自动处理 `/api` 前缀、JSON 响应、Bearer Token、本地 token 存储和错误提示。
   - 用户端手机号登录按钮已改为先尝试 `uni.login` 获取微信 `code`，再调用 `POST /api/auth/wechat-login`。
   - 若正式微信登录因后端配置或开发环境限制失败，会回退到文档提供的开发期 `openid` 测试登录。

2. 用户资料与信息审核
   - 已接入 `GET /api/members/me` 和 `POST /api/members/profile`。
   - 登录成功后会写入 token，并将后端返回的手机号、昵称同步到前端登录状态。
   - 信息审核页提交时会同步昵称和手机号到后端。

3. 积分模块
   - 积分页已接入 `GET /api/points/balance` 获取积分余额。
   - 积分明细已接入 `GET /api/points/records`。
   - 接口不可用时保留本地静态数据兜底，避免页面空白。

4. 学习积分
   - 学习列表已接入 `GET /api/learning/contents`。
   - 学习完成状态已接入 `GET /api/learning/records`。
   - 图文或视频完成后会调用 `POST /api/learning/contents/{content_id}/complete`。
   - 后端不可用时仍保留本地图文、视频演示内容和本地完成记录。

5. 随手拍
   - 随手拍提交已接入 `POST /api/reports`。
   - 我的随手拍已接入 `GET /api/reports`。
   - 列表字段已映射为前端的审核状态、积分、驳回意见和提交时间。

6. 活动
   - 活动列表已接入 `GET /api/activities`。
   - 活动报名已接入 `POST /api/activities/{activity_id}/signup`。
   - 活动扫码签到已接入 `POST /api/activities/{activity_id}/checkin`。
   - 我的活动记录已接入 `GET /api/activities/my-signups`。

7. 助老服务
   - 老人服务任务列表已接入 `GET /api/elder-services/tasks`。
   - 服务反馈提交已接入 `POST /api/elder-services/tasks/{task_id}/feedback`。
   - 服务记录已接入 `GET /api/elder-services/feedbacks`。

8. 扫码优惠临时对接
   - 当前用户端“扫码优惠”仍保留固定商户码交互。
   - 确认优惠时会尝试调用 `GET /api/merchant-products` 和 `POST /api/merchant-products/{product_id}/redeem` 完成一次商品兑换式扣分。
   - 接口失败时仍跳转成功页，便于继续演示既有流程。

## 接口缺失或业务逻辑不匹配

1. 手机号一键登录缺少手机号解密接口
   - 前端交互是微信手机号一键登录，需要通过 `getPhoneNumber` 事件返回的 `code` 或加密数据换取手机号。
   - 当前文档只有 `POST /api/auth/wechat-login`，用于 openid/code 登录，没有“手机号授权结果换手机号”的接口。
   - 目前前端只能用微信登录 code 或测试 openid 登录，手机号以接口返回的 `member.phone` 为准。
   - 建议新增 `POST /api/auth/wechat-phone-login`，或在 `POST /api/auth/wechat-login` 中增加手机号授权参数。
   - 建议请求字段：`login_code`（`uni.login` 返回的登录 code）、`phone_code`（`getPhoneNumber` 返回的手机号授权 code）、`encrypted_data`（兼容旧版微信手机号授权）、`iv`（兼容旧版微信手机号授权）。
   - 建议返回字段：`access_token`、`token_type`、`expires_in`、`member.id`、`member.openid`、`member.phone`、`member.nickname`、`member.profile_audit_status`、`member.is_elderly_care_worker`。

2. 用户信息审核接口缺失
   - 前端信息审核包含姓名、身份类型、服务区域、审核状态、审核意见、对口老人服务关系。
   - 当前后端只有 `POST /api/members/profile`，字段为 `nickname`、`phone`。
   - 建议新增 `GET /api/members/profile-detail`，用于用户端查询本人信息审核详情。
   - `GET /api/members/profile-detail` 建议返回字段：`member_id`、`real_name`、`phone`、`identity_type`、`identity_type_label`、`service_area_code`、`service_area_name`、`audit_status`、`audit_remark`、`submitted_at`、`reviewed_at`、`reviewer_name`、`is_elderly_care_worker`、`elderly_relations`。
   - `audit_status` 建议枚举值：`not_submitted`、`pending`、`approved`、`rejected`。
   - `elderly_relations` 建议数组项字段：`relation_id`、`elder_id`、`elder_name_masked`、`elder_address`、`service_area_code`、`service_area_name`、`relation_status`。
   - 建议新增 `POST /api/members/audit-profile`，用于首次提交审核信息和待审核状态下重新提交信息。
   - `POST /api/members/audit-profile` 建议请求字段：`real_name`、`identity_type`、`service_area_code`。
   - 手机号建议不允许在审核表单中由用户手动修改，后端以微信手机号授权结果或管理员绑定结果为准。
   - 建议新增 `GET /api/member-profile-options`，用于返回身份类型和服务区域选项。
   - `GET /api/member-profile-options` 建议返回字段：`identity_types`、`service_areas`。
   - `identity_types` 建议数组项字段：`value`、`label`。
   - `service_areas` 建议数组项字段：`code`、`name`。
   - 管理后台建议补充 `GET /api/admin/member-audits`、`GET /api/admin/member-audits/{audit_id}`、`POST /api/admin/member-audits/{audit_id}/approve`、`POST /api/admin/member-audits/{audit_id}/reject`。
   - 管理后台审核列表建议返回字段：`audit_id`、`member_id`、`real_name`、`phone`、`identity_type_label`、`service_area_name`、`audit_status`、`submitted_at`。
   - 管理后台审核详情建议返回字段：`audit_id`、`member_id`、`real_name`、`phone`、`identity_type`、`identity_type_label`、`service_area_code`、`service_area_name`、`audit_status`、`audit_remark`、`submitted_at`、`reviewed_at`、`reviewer_id`、`reviewer_name`、`elderly_relations`。
   - 驳回接口建议请求字段：`audit_remark`。

3. 活动接口缺少报名取消和完整记录详情
   - 需求中用户报名后允许取消报名，但当前文档没有取消报名接口。
   - `GET /api/activities/my-signups` 只返回报名 ID、活动 ID、报名时间，缺少活动标题、地点、时间、签到状态、补签状态、积分发放状态。
   - 前端记录页只能用活动 ID 做兜底展示，无法完整还原“已报名/已完成活动记录”。
   - 建议新增 `POST /api/activities/{activity_id}/cancel-signup`，或新增 `DELETE /api/activities/{activity_id}/signup`。
   - 取消报名接口建议返回字段：`signup_id`、`activity_id`、`signup_status`、`cancelled_at`。
   - `GET /api/activities/my-signups` 建议返回字段：`signup_id`、`activity_id`、`title`、`body`、`location`、`start_time`、`end_time`、`points`、`signup_status`、`signed_up_at`、`cancelled_at`、`checkin_status`、`checkin_at`、`makeup_checkin_status`、`point_status`、`point_record_id`。
   - `signup_status` 建议枚举值：`joined`、`cancelled`、`ended`。
   - `checkin_status` 建议枚举值：`not_checked`、`checked`、`makeup_checked`。
   - `point_status` 建议枚举值：`not_granted`、`granted`。

4. 活动签到码来源不清楚
   - 前端扫码后需要拿到 `checkin_code` 调用签到接口。
   - 文档说明后台生成签到码和二维码图片，但用户端没有获取活动签到二维码内容格式的说明。
   - 需要明确二维码扫码结果是纯 `checkin_code`，还是包含活动 ID、URL、JSON 或其他载荷。
   - 建议活动详情或后台任务详情返回 `checkin_code`、`checkin_qrcode_url`、`checkin_start_time`、`checkin_end_time`。
   - 若二维码内容使用 JSON，建议字段为 `type`、`activity_id`、`checkin_code`、`expires_at`、`signature`。
   - 若二维码内容使用 URL，建议 URL query 包含 `activity_id`、`checkin_code`、`expires_at`、`signature`。
   - `POST /api/activities/{activity_id}/checkin` 建议请求字段：`checkin_code`、`scan_payload`。
   - 签到接口建议返回字段：`checkin_id`、`activity_id`、`checkin_status`、`checkin_at`、`point_status`、`point_record_id`、`review_comment`。

5. 助老服务任务分配口径需要调整
   - 最新业务逻辑为街道后台给小哥配置固定对口老人服务关系，小哥不需要领取任务，也不需要领取审核。
   - 老人服务页面应直接展示当前登录小哥被分配的老人服务事项，并提供“提交反馈”入口。
   - 当前 `GET /api/elder-services/tasks` 需要明确是否只返回当前小哥已分配的任务；如果仍返回公开任务列表，需要增加“按当前小哥/服务关系过滤”的接口或字段。
   - `POST /api/elder-services/tasks/{task_id}/feedback` 需要能校验该任务是否属于当前小哥的对口服务关系，避免提交非本人分配任务。
   - 建议新增 `GET /api/elder-services/my-tasks`，只返回当前登录小哥已分配的老人服务事项。
   - `GET /api/elder-services/my-tasks` 建议返回字段：`task_id`、`title`、`description`、`location`、`points`、`service_type`、`repeat_type`、`weekly_day`、`monthly_day`、`deadline`、`assigned_at`、`relation_id`、`elder_id`、`elder_name_masked`、`elder_address`、`feedback_status`、`latest_feedback_id`、`resubmit_count`、`max_resubmit_count`。
   - `service_type` 建议枚举值：`regular`、`urgent`。
   - `repeat_type` 建议枚举值：`weekly`、`monthly`。
   - `feedback_status` 建议枚举值：`not_submitted`、`pending`、`approved`、`rejected`。
   - `POST /api/elder-services/tasks/{task_id}/feedback` 建议请求字段：`content`、`image_urls`。
   - 反馈提交接口建议返回字段：`feedback_id`、`task_id`、`status`、`submitted_at`、`image_urls`、`review_comment`、`point_record_id`。

6. 助老服务记录字段不足
   - `GET /api/elder-services/feedbacks` 当前返回 `task_id`、`content`、`image`、`status`、`review_comment`、`point_record_id`、`created_at`。
   - 前端记录页需要展示任务标题、服务地点、任务积分、分配时间、反馈时间、完成时间、驳回后重新提交次数。
   - 当前接口无法完整支撑页面展示。
   - `GET /api/elder-services/feedbacks` 建议返回字段：`feedback_id`、`task_id`、`title`、`description`、`location`、`points`、`service_type`、`assigned_at`、`submitted_at`、`completed_at`、`status`、`review_comment`、`reviewed_at`、`point_record_id`、`image_urls`、`resubmit_count`、`max_resubmit_count`、`relation_id`、`elder_id`、`elder_name_masked`。
   - `status` 建议枚举值：`pending`、`approved`、`rejected`。

7. 图片上传接口缺失
   - 随手拍和老人服务反馈都涉及图片上传。
   - 当前接口只接受 `image` 字符串，没有独立上传接口、文件表单格式、图片 URL 生成规则、单张大小限制和多图字段规范。
   - 前端可以先限制图片格式、选择数量、单张大小、是否至少上传 1 张，并在提交前阻止明显不合规的文件。
   - 后端仍需要做最终校验，前端限制不能替代服务端校验，否则接口被绕过时仍可能写入超大文件、非法格式或不符合数量要求的数据。
   - 前端当前只能把本地临时路径作为 `image` 传入，真机联调时通常需要先上传文件获取服务端 URL，再把 URL 或 URL 数组提交到业务接口。
   - 建议后端明确上传接口使用 `multipart/form-data` 还是直传云存储，明确单图字段名、多图字段名、返回 URL 结构、文件大小上限和允许的 MIME 类型。
   - 建议新增 `POST /api/uploads/images`。
   - 若使用 `multipart/form-data`，建议请求字段为 `files`、`business_type`、`related_id`。
   - `files` 支持多文件上传；单文件上传时仍使用 `files`，避免单图和多图字段分裂。
   - `business_type` 建议枚举值：`report`、`elder_service_feedback`、`civic_feedback`。
   - `related_id` 用于已存在业务记录的补充上传，新增业务提交前上传时允许为空。
   - 建议返回字段：`files`。
   - `files` 数组项建议字段：`file_id`、`url`、`original_name`、`size`、`mime_type`、`width`、`height`、`created_at`。
   - 建议允许 MIME 类型：`image/jpeg`、`image/png`、`image/webp`。
   - 建议单张图片大小上限：`10MB`。
   - 建议随手拍图片数量限制：最少 `1` 张，最多 `10` 张。
   - 建议老人服务反馈图片数量限制：最少 `1` 张，最多 `10` 张。
   - 建议社情民意材料图片数量限制：最少 `1` 张，最多 `6` 张。
   - 建议业务提交接口统一使用 `image_urls` 数组字段，不再只使用单个 `image` 字符串字段。

8. 随手拍多图与分类字段不匹配
   - 需求要求随手拍至少 1 张、最多 10 张图片，并有问题分类。
   - 当前 `POST /api/reports` 只有 `title`、`description`、`image`、`location`。
   - 前端目前将问题分类映射到 `title`，只提交第一张图片到 `image`。
   - 建议新增 `GET /api/report-categories`。
   - `GET /api/report-categories` 建议返回字段：`code`、`name`、`sort_order`、`is_active`。
   - 建议调整 `POST /api/reports` 请求字段为：`category_code`、`description`、`image_urls`、`location_name`、`address_detail`。
   - `image_urls` 建议为字符串数组，数量限制为最少 `1` 张、最多 `10` 张。
   - `GET /api/reports` 建议返回字段：`report_id`、`category_code`、`category_name`、`description`、`image_urls`、`location_name`、`address_detail`、`points`、`status`、`review_comment`、`point_record_id`、`created_at`、`reviewed_at`。
   - `status` 建议枚举值：`pending`、`approved`、`rejected`。

9. 社情民意和问题反馈接口缺失
   - 用户端服务页包含“社情民意”和“问题反馈”两个入口。
   - 当前 API 文档没有对应提交、列表、回复、采纳、人工加分接口。
   - 这两个页面暂时保留静态演示。
   - 社情民意建议新增 `POST /api/civic-feedbacks`。
   - `POST /api/civic-feedbacks` 建议请求字段：`title`、`content`、`material_urls`。
   - 社情民意建议新增 `GET /api/civic-feedbacks`。
   - `GET /api/civic-feedbacks` 建议返回字段：`feedback_id`、`title`、`content`、`material_urls`、`status`、`points`、`reply`、`point_record_id`、`created_at`、`reviewed_at`。
   - 社情民意 `status` 建议枚举值：`submitted`、`accepted`、`rejected`。
   - 问题反馈建议新增 `POST /api/problem-feedbacks`。
   - `POST /api/problem-feedbacks` 建议请求字段：`title`、`content`。
   - 问题反馈建议新增 `GET /api/problem-feedbacks`。
   - `GET /api/problem-feedbacks` 建议返回字段：`feedback_id`、`title`、`content`、`status`、`reply`、`created_at`、`replied_at`。
   - 问题反馈 `status` 建议枚举值：`submitted`、`processing`、`replied`。

10. 商户固定二维码优惠与后端商品兑换逻辑不一致
   - 当前前端需求是商户展示固定二维码，用户扫码后按后台统一比例或规则抵扣积分。
   - 后端文档提供的是商品兑换：`merchant-products`、`product-redemptions`。
   - 两者业务模型不同，商品兑换不能完全替代固定二维码抵扣。
   - 需要后端补充商户固定码识别、固定抵扣规则查询、用户确认抵扣、用户抵扣记录和商户流水接口，或明确一期改为商品兑换模式。
   - 建议新增 `POST /api/fixed-discounts/resolve`，用于用户扫码后解析固定优惠二维码。
   - `POST /api/fixed-discounts/resolve` 建议请求字段：`qr_payload`。
   - 固定码解析接口建议返回字段：`merchant_id`、`merchant_name`、`merchant_address`、`fixed_code_id`、`rule_id`、`rule_name`、`deducted_points`、`discount_amount`、`rule_version`、`is_available`、`unavailable_reason`。
   - 建议新增 `POST /api/fixed-discounts/redeem`，用于用户确认扣分。
   - `POST /api/fixed-discounts/redeem` 建议请求字段：`fixed_code_id`、`rule_id`、`rule_version`。
   - 用户确认扣分接口建议返回字段：`order_id`、`merchant_id`、`merchant_name`、`deducted_points`、`discount_amount`、`rule_name`、`status`、`created_at`、`point_record_id`。
   - 建议新增 `GET /api/fixed-discounts/records`，用于用户端查看本人扫码优惠记录。
   - 用户端扫码优惠记录建议返回字段：`order_id`、`merchant_id`、`merchant_name`、`deducted_points`、`discount_amount`、`rule_name`、`status`、`created_at`、`point_record_id`。

11. 积分明细缺少余额快照
   - 前端积分明细原设计展示每条记录后的余额。
   - 当前 `GET /api/points/records` 返回 amount、source_type、reason、created_at，但没有 `balance_after`。
   - 前端目前只能展示变动值，余额快照需要后端补充字段或前端按完整流水自行计算。
   - 建议 `GET /api/points/records` 返回字段增加 `balance_after`。
   - 建议积分记录字段完整返回：`record_id`、`amount`、`change_type`、`source_type`、`source_id`、`reason`、`balance_after`、`created_at`。
   - `change_type` 建议枚举值：`income`、`expense`。

12. 学习内容缺少内容类型字段
   - 前端需要区分图文学习和视频学习。
   - 当前学习内容字段没有 `content_type` 或 `media_type`，只有 `cover` 和 `body`。
   - 前端目前只能根据 `cover` 是否像视频 URL 做粗略判断，建议后端补充明确类型字段和视频 URL 字段。
   - 建议 `GET /api/learning/contents` 和 `GET /api/learning/contents/{content_id}` 返回字段增加 `content_type`、`cover_url`、`image_urls`、`video_url`。
   - `content_type` 建议枚举值：`article`、`image`、`video`。
   - 图文内容建议使用字段：`title`、`body`、`cover_url`、`points`、`required_seconds`、`is_active`。
   - 图片内容建议使用字段：`title`、`body`、`image_urls`、`points`、`required_seconds`、`is_active`。
   - 视频内容建议使用字段：`title`、`body`、`cover_url`、`video_url`、`points`、`required_seconds`、`is_active`。
   - 学习记录建议返回字段：`record_id`、`content_id`、`learned_seconds`、`is_completed`、`completed_at`、`point_record_id`。

## 当前前端处理策略

1. 所有已接接口均采用“接口优先、失败回落本地静态数据”的方式，保证后端未启动、token 失效或字段不完整时页面仍可展示。
2. 对接口缺失的功能不强行伪造后端逻辑，保留本地交互演示，并在本文件中记录对接问题。
3. 后续后端接口补齐后，可优先从 `apps/user-mp/src/api/user.ts` 和 `apps/user-mp/src/api/mappers.ts` 两处调整，不需要大面积重写页面。

## 已按现有接口接入的商户端功能

1. 商户登录基础链路
   - 商户端默认接口地址同样配置为 `https://8000.frp.chatgqt.top/api`。
   - 已新增商户端独立请求封装，商户 token 使用 `cs_street_merchant_access_token` 单独存储，不与用户端 token 混用。
   - 商户手机号登录按钮已改为先尝试 `uni.login` 获取微信 `code`，再调用 `POST /api/merchant/auth/wechat-login`。
   - 若正式微信登录因后端配置或开发环境限制失败，会回退到文档提供的开发期 `merchant-openid` 测试登录。

2. 商户资料
   - 已接入 `GET /api/merchant/me`。
   - 登录后会将后端返回的商户名称、联系人、手机号、地址同步到首页、我的页和码牌展示页。

3. 商户流水
   - 流水页已接入 `GET /api/merchant/redemptions`。
   - 已将商品兑换记录映射为商户端流水展示，包含兑换编号、用户 ID、商品名称、消耗积分、创建时间和交付状态。
   - 待交付记录可调用 `POST /api/merchant/redemptions/{redemption_id}/complete` 确认交付。

4. 月度结清
   - 结清页已接入 `GET /api/merchant/redemptions/summary?month=YYYY-MM`。
   - 已展示本月兑换笔数、商品种类数和消耗积分合计。
   - 后端不可用时保留本地静态月度数据兜底。

5. 商户首页数据
   - 首页已在登录后尝试读取月度兑换汇总，展示本月积分合计和兑换笔数。
   - 未登录时仍保留二维码打底图和登录遮罩，避免页面空白。

## 商户端接口缺失或业务逻辑不匹配

1. 商户手机号一键登录缺少手机号解密接口
   - 商户端交互同样是手机号一键登录，但后端只有 `POST /api/merchant/auth/wechat-login`。
   - 当前接口返回商户资料中的 `phone`，但没有处理微信手机号授权结果的接口。
   - 前端目前只能用微信登录 code 或测试 openid 登录，手机号以 `merchant.phone` 为准。
   - 建议新增 `POST /api/merchant/auth/wechat-phone-login`，或在 `POST /api/merchant/auth/wechat-login` 中增加手机号授权参数。
   - 建议请求字段：`login_code`、`phone_code`、`encrypted_data`、`iv`。
   - 建议返回字段：`access_token`、`token_type`、`expires_in`、`merchant.id`、`merchant.openid`、`merchant.name`、`merchant.contact`、`merchant.phone`、`merchant.address`、`merchant.bind_status`。
   - `bind_status` 建议枚举值：`bound`、`unbound`、`disabled`。

2. 商户固定二维码接口缺失
   - 当前商户端需求是每个商户有一个固定二维码，用户扫描后发起积分抵扣。
   - 后端商户资料接口没有固定二维码 ID、二维码内容、二维码图片 URL 或二维码刷新/失效规则。
   - 前端目前用 `MCH-{merchant.id}` 和本地二维码样式作为展示兜底。
   - 建议新增 `GET /api/merchant/fixed-code`。
   - `GET /api/merchant/fixed-code` 建议返回字段：`merchant_id`、`merchant_name`、`fixed_code_id`、`qr_payload`、`qrcode_url`、`status`、`created_at`、`updated_at`。
   - `status` 建议枚举值：`active`、`disabled`。
   - `qr_payload` 建议使用固定字符串或 URL，内容应能被用户端扫码解析接口识别。
   - 如果二维码图片由后端生成，`qrcode_url` 返回图片地址；如果二维码由前端根据 payload 生成，`qrcode_url` 可以为空。

3. 固定优惠规则接口缺失
   - 当前需求为管理员统一设置抵扣比例或固定抵扣规则，商户端只展示。
   - 后端文档没有固定抵扣规则查询接口，也没有返回“多少积分等于多少元”或“单次抵扣规则”的字段。
   - 前端固定优惠规则页仍使用本地静态数据。
   - 建议新增 `GET /api/merchant/fixed-discount-rule`。
   - `GET /api/merchant/fixed-discount-rule` 建议返回字段：`rule_id`、`rule_name`、`deducted_points`、`discount_amount`、`rule_version`、`effective_at`、`updated_at`、`updated_by`。
   - 商户端只读展示 `deducted_points` 和 `discount_amount`，不提供编辑接口。
   - 如果固定优惠规则按街道统一配置，建议接口返回当前商户适用的全局规则快照。

4. 商户流水模型与固定二维码抵扣不一致
   - 后端商户流水接口是商品兑换记录 `merchant/redemptions`。
   - 前端原业务是用户扫描商户固定二维码后产生积分抵扣流水。
   - 商品兑换记录缺少固定码核销所需的优惠金额、抵扣规则、核销门店和用户确认状态等字段。
   - 建议新增 `GET /api/merchant/fixed-discount-orders`。
   - `GET /api/merchant/fixed-discount-orders` 建议查询参数：`page`、`page_size`、`status`、`start_date`、`end_date`。
   - 商户固定优惠流水建议返回字段：`order_id`、`merchant_id`、`merchant_name`、`member_id`、`member_name_masked`、`member_phone_masked`、`fixed_code_id`、`rule_id`、`rule_name`、`deducted_points`、`discount_amount`、`status`、`created_at`、`point_record_id`、`settlement_status`、`settlement_id`。
   - `status` 建议枚举值：`success`、`failed`。
   - `settlement_status` 建议枚举值：`unsettled`、`included`、`settled`。
   - 商户端已删除撤销能力，因此不需要新增商户撤销扣分接口。

5. 月度结清缺少金额字段和历史列表
   - `GET /api/merchant/redemptions/summary` 只返回兑换笔数、商品种类数、积分合计。
   - 商户端原页面需要展示本月折算金额、历史结清记录、结清状态和结清时间。
   - 当前前端只能展示积分合计，折算金额继续为静态兜底或 0。
   - 建议新增 `GET /api/merchant/settlements`。
   - `GET /api/merchant/settlements` 建议查询参数：`page`、`page_size`、`period_type`、`year`、`month`、`status`。
   - 结算列表建议返回字段：`settlement_id`、`merchant_id`、`period_label`、`period_type`、`period_start`、`period_end`、`order_count`、`total_points`、`total_discount_amount`、`status`、`processed_at`、`processor_name`、`remark`。
   - `period_type` 建议枚举值：`month`、`quarter`、`year`、`custom`。
   - `status` 建议枚举值：`pending`、`processing`、`settled`。
   - 建议新增 `GET /api/merchant/settlements/{settlement_id}`。
   - 结算详情建议返回字段：`settlement_id`、`merchant_id`、`merchant_name`、`period_label`、`period_type`、`period_start`、`period_end`、`order_count`、`total_points`、`total_discount_amount`、`status`、`processed_at`、`processor_name`、`remark`、`orders`。
   - `orders` 数组项建议字段：`order_id`、`member_name_masked`、`deducted_points`、`discount_amount`、`created_at`。

6. 商户商品管理接口未覆盖当前页面
   - 后端商品兑换模型依赖商户商品，但商户端目前没有商品管理页面。
   - 如果一期确认采用商品兑换模式，需要明确商品由后台管理还是商户端维护，以及商户端是否需要新增商品列表、库存、上下架页面。
   - 如果一期继续采用固定二维码优惠模式，商户端不需要商品列表、库存、上下架接口。
   - 如果一期改为商品兑换模式，建议补充 `GET /api/merchant/products`、`POST /api/merchant/products`、`PUT /api/merchant/products/{product_id}`、`POST /api/merchant/products/{product_id}/enable`、`POST /api/merchant/products/{product_id}/disable`。
   - 商品字段建议包含：`product_id`、`merchant_id`、`name`、`image_url`、`description`、`points_required`、`stock`、`is_active`、`created_at`、`updated_at`。

7. 用户端和商户端二维码流转协议未定义
   - 用户端扫码结果、商户端固定码内容、后端校验规则之间还没有统一协议。
   - 需要明确二维码内容是固定字符串、URL、JSON、短码，还是包含签名和过期时间。
   - 需要明确用户扫码后调用哪个接口完成抵扣或兑换，以及商户端如何实时看到流水变化。
   - 建议固定二维码内容采用 URL 或 JSON 之一，不建议不同商户混用多种格式。
   - JSON payload 建议字段：`type`、`merchant_id`、`fixed_code_id`、`version`、`signature`。
   - URL payload 建议 query 字段：`type`、`merchant_id`、`fixed_code_id`、`version`、`signature`。
   - `type` 建议固定为 `merchant_fixed_discount`。
   - 用户端扫码后建议先调用 `POST /api/fixed-discounts/resolve` 展示商户和优惠规则，再调用 `POST /api/fixed-discounts/redeem` 完成扣分。
   - 商户端流水建议通过 `GET /api/merchant/fixed-discount-orders` 拉取最新记录；如果后续需要实时刷新，可增加 WebSocket 或服务端推送能力。

# 第三次对接后端待办说明

更新时间：2026-06-29

本文用于给后端工程师说明第三次对接后仍需要补做或修正的事项。本文不记录前端已经完成了什么，也不展开具体字段；具体接口字段、请求响应结构请看《前端API需求文档（小程序端）.md》。

## 一、先统一本轮业务口径

商户端已经不再按“商品兑换”“商品交付”“商户确认核销”来理解业务。当前正确口径是：

用户扫描商户固定二维码后，输入本次要抵扣的积分，系统按照后台统一配置的积分兑元比例折算金额并扣减积分。系统只记录积分流水，不记录商品订单，也不需要商户确认交付。

所以后端后续不要再把商品兑换接口作为扫码优惠主链路，也不要再让商户端围绕商品、订单、交付状态继续扩展功能。

## 二、商户扫码积分支付仍需补齐

商户固定码、用户扫码支付、商户积分流水这条主链路已经有基础接口，但还不够支撑真实业务和演示稳定性。

后端需要继续补齐商户端能看到的当前积分兑元比例，让商户知道当前使用的规则版本。商户流水也需要支持按日期、月份筛选，并返回服务端汇总结果。现在前端临时拉取一批流水后自己统计，只适合演示，数据量变大后会不可靠。

商户“结清页”还缺真实结算记录。当前页面只能用积分流水临时汇总，不能表示真正的结算批次、处理状态、处理时间和备注。后端需要提供商户端可读取的结算记录能力。

## 三、微信手机号正式登录需要完成

用户端和商户端目前还没有真正完成微信手机号一键登录闭环。后端需要支持微信 `getPhoneNumber` 返回的手机号授权 code，换取真实手机号并完成账号绑定。

这件事会影响微信审核，也会影响未登录态清理后的真实使用，所以优先级较高。

同时，所有需要登录的接口应统一 token 过期错误返回。前端已经做了登录过期引导，但后端如果不同接口返回不同错误结构，用户扫码支付、查看记录时仍可能出现体验不一致。

## 四、用户审核资料需要接入后端状态

用户端现在有姓名、身份类型、服务区域和审核状态流程，但后端还没有完整承接。

后端需要让小程序能提交审核资料，并能在登录后读取真实审核状态、驳回原因、服务区域、是否配置对口老人服务等信息。前端业务入口会根据审核状态决定是否允许继续操作，因此这个状态不能长期只存在本地。

## 五、随手拍需要从单图模型升级

随手拍页面目前是按真实业务做的：问题分类、问题位置、问题描述、现场图片，且页面支持多图。

后端现在仍偏单图字段，不够匹配前端和业务展示。需要补齐多图、分类、位置字段，并保证用户提交后能在“我的随手拍”里看到审核状态、驳回原因、发放积分等结果。

如果后端短期不能支持多图，需要明确产品口径改为只允许一张图；否则前端和用户预期会不一致。

## 六、社情民意和问题反馈仍是静态演示

用户端已经有“社情民意”和“问题反馈”入口，但这两块目前还没有真实接口支撑。

社情民意需要支持用户提交文字和图片材料，之后能看到是否被采纳、后台回复和是否加分。

问题反馈需要支持用户提交文字反馈，之后能看到处理状态和回复内容。

这两个模块如果不补，服务页里会长期保留静态演示数据，无法进入真实业务闭环。

## 七、老人服务要按“本人分配任务”实现

老人服务的业务口径不是用户自己领取公开任务，而是由后台配置小哥和老人之间的对口关系，小哥只看自己被分配的服务事项。

后端需要提供“我的老人服务任务”能力，并返回当前任务是否已提交反馈、反馈是否审核中、是否已通过、是否被驳回。前端已经按这些状态调整了按钮逻辑，如果后端仍返回公开任务列表，会和页面逻辑对不上。

老人服务反馈也需要明确重复提交规则：审核中和已通过不能重复提交，驳回后允许重新提交。

## 八、志愿活动状态和签到码需要明确

活动列表需要直接告诉前端当前用户是否已报名、是否已签到、签到是否待审核或已确认。否则用户已经报名的活动仍可能在列表里显示“可报名”。

活动签到二维码格式也需要固定下来。建议和商户固定码一样使用统一的自定义协议格式，里面带活动 ID 和签到码。前端扫码后把签到码交给后端校验。

签到状态也需要统一口径：`pending` 应表示已扫码签到但待审核，`confirmed` 表示签到审核通过。前端会把这两种状态都展示为“已签到”，避免用户重复扫码。

## 九、学习内容媒体字段需要稳定

学习内容现在需要支持图文、图片、视频三类。后端数据库里虽然有分类，但接口返回必须稳定，让前端能够直接按类型渲染。

后端需要保证封面、正文图片、视频地址都是小程序可访问的完整地址。视频内容必须返回可播放的视频地址，且对应域名需要满足微信小程序播放要求。

完成学习接口也需要做幂等处理，同一用户同一内容不能重复发积分。学习时长、是否已完成、完成时间、积分流水也要能让前端读取。

## 十、积分明细来源需要统一

积分明细页是用户端核对积分变化的重要页面。后端需要稳定返回每条流水的来源、原因、变动后余额，以及商户支付对应的商户名称和折算金额。

学习、随手拍、志愿签到、老人服务、社情民意、商户积分支付、人工调整等来源需要统一枚举值，避免前端每次为新来源单独兼容。

## 十一、上传文件能力需要稳定

图片上传是随手拍、社情民意、老人服务反馈都会用到的基础能力。

后端需要确保上传接口能稳定接收多图，返回完整可访问 URL，并限制图片类型、大小和数量。前端现在已经做了部分限制，但后端仍必须做最终校验。

## 十二、建议后端优先顺序

1. 先完成用户端和商户端微信手机号正式登录，并统一 token 过期错误。
2. 补用户审核资料提交和审核状态读取。
3. 补随手拍多图、分类、位置和审核结果展示能力。
4. 补老人服务“本人分配任务”和反馈状态规则。
5. 补志愿活动用户报名状态、签到二维码格式和签到状态口径。
6. 补商户流水日期筛选、汇总和商户端结算记录。
7. 补社情民意和问题反馈真实接口。
8. 修正学习内容媒体字段和完成学习幂等发分。
9. 稳定上传文件和积分明细来源枚举。
